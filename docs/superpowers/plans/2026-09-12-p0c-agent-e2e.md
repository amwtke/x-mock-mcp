## Task C1: 准备入口、场景快照、轨迹与右端导出

- 为 store 编写版本冲突测试：版本 1 被环境 A 固定后保存版本 2，A 仍使用版本 1；两个相同 expected_version 的并发保存只能成功一次。运行 `go test ./internal/scenario -run 'TestSnapshot|TestVersionConflict' -count=1` 确认失败。
- 场景外层信封定义：

```go
package scenario

import "encoding/json"

type Document struct {
    ID string `json:"id"`
    Version int64 `json:"version"`
    PluginID string `json:"plugin_id"`
    PluginVersion string `json:"plugin_version"`
    ContractID string `json:"contract_id"`
    ContractVersion int `json:"contract_version"`
    Input json.RawMessage `json:"input,omitempty"`
    Body json.RawMessage `json:"body"`
}

type Snapshot struct {
    Document Document `json:"document"`
    SHA256 string `json:"sha256"`
    PluginDigests map[string]string `json:"plugin_digests"`
}
```

Store 提供 Put(ctx, document, expectedVersion)、Get(ctx, id, version)、Freeze(ctx, id, version, pluginDigests)。准备用例按固定的已启用右端版本调用 A2 ScenarioPreparer，ProjectRoot 由 daemon 提供。无 candidate 时仅检查资料，有 candidate 时返回报告/规范产物。MySQL Document.Input 保存原始 QA 和证据引用，Body 保存编译场景；非准备插件可以不带 Input。

Put 校验 ScenarioSchema、大小/ID/版本，声明 scenario.prepare 时以 Document.Input/Body 再调用 Prepare，要求 ready=true 后保存规范化结果；采用比较版本后 temp+rename 原子落盘。创建环境时右端重新验证语义、源码/DDL 摘要与包版本；工作区变化返回 STALE_EVIDENCE，要求新版本。离线回放指不访问模型/数据库，仍要求匹配的本地源码与运行依赖。

- 编写准备无监听、资料缺口、插件未启用、摘要漂移、绕过 prepare 直接 Put 非法候选、保存冲突测试。断言核心只转发 opaque Input/Body，没有 SQL 或 QA 必填字段分支。

- trace 记录 request_id、binding_id、connection_id、场景/插件版本、SQL 规则 ID、状态版本、事务阶段、结果来源、耗时和结构化错误。确认成功的生成另保存原始 Need.Context、候选 EntityFill 与最终响应，供通用 Capture 使用。核心将插件事件作为 opaque 载荷记录，不解析 SQL。事件拥有递增 seq，按 run_id 保存；密码/token/认证报文不入轨迹；64 MiB 上限明确结束运行。
- 实现 Export：只选取显式 request_id 的成功生成，构造 A2 ExportSpec（Snapshot=Document.Body，Captures 包含原始请求、候选、生成上下文及最终结果），交右端 ScenarioExporter。Input 原样保留，候选 Body 重新 Prepare/Schema 校验后返回；不修改运行 Snapshot 或自动发布。
- MySQL 导出仅将确认的不可变参考实体 slot 合入初始表数据并标记物化；保留 SQL/参数域、动作、QA/API 断言、空购物车及自增种子。不能把当前购物车终态或 SELECT 投影结果当初始数据。未选 slot 仍缺数据时，候选只能用于 AgentFill，不能声称已可 StrictReplay。
- MySQL verify 校验 verification 中的最终表状态、必需写操作和 `expect_calls` 的 min/max（key=statement ID），不统计系统查询。HTTP/UI 断言由实际测试执行，不由右端制造其成功报告。
- 测试导出排除未选、取消和失败结果；同实体冲突拒绝；原初态购物车仍为空、商品生成可复用、重跑还需要 INSERT/UPDATE。超出 max 当场失败、低于 min/最终状态错误在完成时失败。所有数据库格式拼装留在右端包。
- 运行 `go test -race ./internal/scenario ./internal/trace ./plugins/right/mysql-mock -count=1`。提交：`feat: persist immutable scenarios and plugin-owned exports`。

## Task C2: AgentFill 与请求状态机

- 定义测试 Clock 接口 Now() time.Time、AfterFunc(duration, callback) CancelFunc；testkit 实现 Advance(duration)，用于可重复的截止时间与租约测试。网络 context 取消仍独立生效。
- 测试同一请求两个并发领取只能成功一个；过期 lease 不可回填；重复相同结果幂等而冲突结果失败；运行 A 的令牌不能回填运行 B。先运行 `go test ./internal/generation -count=1` 观察失败。
- 定义状态机及原子操作：

```text
pending -> leased -> resolving -> resolved
leased -> pending                 lease 到期且业务 deadline 尚未到达
pending/leased/resolving -> expired/cancelled

Enqueue(ctx, need) -> wait for validated result or cancellation
Next(run_id, owner_token, limit, wait_ms) -> leased requests + lease tokens
Resolve(run_id, request_id, owner_token, lease_token, candidate) -> completion ack
CancelRequest(request_id, reason)
CancelRun(run_id, reason)
```

Next 上限 8 件，wait_ms 范围 0–2000。队列每运行最多 128 个未完成请求、全项目最多 512 个。满队列立即返回 QUEUE_FULL。业务 deadline 不因重领而延长，lease 到期时间取租约与业务 deadline 的较小值。

- 一个 run 同时只有一个生成 owner。首次 Next 可以领取 owner 并返回随机 owner_token；其他客户端仍可看 status/trace，但没有 token 的 Next 返回 owner 已占用。显式 `takeover=true` 必须附 expected_owner_epoch；成功后递增 epoch、废止旧 token 与旧 lease，并将仍有时间的请求放回 pending。该操作由共享项目访问凭据授权，不能由超时自动触发。
- 结果处理采用通用 schema 校验 → lease/deadline 二次核对 → per-request resolving 状态 → 将候选结果送给等待中的 AgentFill.Resolve → A5 的 Binding Router 调用右端 Complete → OutcomeObserver 报告最终结果。队列通过 ReportOutcome(request_id, payload, err) 接收该报告；mock_requests_resolve 等待这个完成 ack，而非仅报告候选数据已接收。全局队列锁不能跨 RPC 或等待持有。通用 schema 校验不通过时保持有效 lease，允许在时限内修正；右端 Complete 拒绝旧状态或语义不合法的数据则结束原请求，不生成无界重试循环。
- completed 结果保留其规范 JSON 摘要与完成 ack 直到运行清理。同一请求的重复相同候选返回已有 ack，不再次调用右端 Complete；不同候选返回 STATE_CONFLICT。若右端进程在 Complete 期间退出，运行失败，不猜测其是否已经应用结果。
- StrictReplay.Resolve 立即返回 UNMATCHED_REQUEST；AgentFill.Resolve 入队并有界等待。只接受这两种策略；未知策略拒绝，不提供独立模型配置或凭据读取路径。
- 运行 `go test -race ./internal/generation -count=1`，覆盖取消与 resolve 同时发生、过期 token、takeover、队列满、schema 错误。提交：`feat: add bounded agent request leasing and resolution`。

## Task C3: 后台任务与 daemon 应用服务

- 定义 JobSpec：Name、Argv([]string)、WorkingDirectory、Env(map)、TimeoutMS。任务来自项目配置，run_start 只接受具名任务与 environment_id，不能传入新的任意 shell 字符串。
- 用 testkit 子进程编写 run_start 快速返回、超时结束、停止整个进程组、输出超限和非零退出码测试。运行 `go test ./internal/run -count=1` 确认失败。
- run_start 在短临界区中分配 run_id、把环境绑定到该 run、创建后台任务并返回。P0 每个环境只运行一个任务，重跑创建新环境。任务生命周期与发起它的 MCP 请求 context 分离；该 MCP 请求返回不会取消后台测试。
- 任务按 Argv 使用 exec.Command，复制允许的环境变量并注入 mock 端点。Darwin/Linux 使用所属进程组；stop 先取消待处理请求与测试进程，5 秒后结束仍存活的所属组，并 Wait 回收。插件在父 IPC EOF 时关闭自己的监听并退出，避免 daemon 崩溃留下服务。
- 运行完成后依次收集退出码、未匹配/协议错误、场景 Verify 报告和未完成请求状态。只有退出码为 0 且这些约束全部通过时才是 succeeded。运行已终止后拒绝旧连接继续提交业务请求。
- AppService 整合 catalog、环境/binding、scenario、queue、run 和 trace；所有外部控制入口调用同一套用例。daemon 持有项目实例锁，ready 文件只记录 PID、实例随机 ID、启动时间、HTTP 地址；token 文件单独设置用户读写权限。旧 ready 文件不能作为结束某个无关 PID 的依据。
- 测试同一项目重复 serve 明确报告已有实例；端口被占用时失败且不结束占用者；两个项目互不干扰。运行 `go test -race ./internal/run ./internal/app -count=1`。提交：`feat: orchestrate background test runs and daemon ownership`。

## Task C5: Spring Boot 购物、浏览器点击与自动协作验收

- 按 [QA 购物示例](../../templates/mysql-qa-scenario.md) 和 [DDL/API 契约](../specs/2026-09-12-mysql-qa-scenario-contract.md) 创建 ShopApplication、ProductController、CartController、CartService、ShopRepository 与静态页面。这是独立样例，接入真实工程时分析其既有代码，不改真实业务代码来迎合 mock。
- ShopRepository 使用 JdbcTemplate 与显式 DTO：Product(id,name,priceCents,stock,status)、CartItem(id,userId,productId,quantity)。登记以下模板，使用 BIGINT/VARCHAR 元数据；prepared 参数域允许 U1=2001、U2=2002、P1=1001、quantity=1 和本场景生成的 cart ID 5001：

```sql
SELECT id, name, price_cents, stock, status FROM products WHERE status = ? ORDER BY id;
SELECT id, name, price_cents, stock, status FROM products WHERE id = ?;
SELECT id, user_id, product_id, quantity FROM cart_items WHERE user_id = ? AND product_id = ?;
SELECT id, user_id, product_id, quantity FROM cart_items WHERE user_id = ? ORDER BY id;
INSERT INTO cart_items (user_id, product_id, quantity) VALUES (?, ?, ?);
UPDATE cart_items SET quantity = quantity + ? WHERE id = ? AND user_id = ?;
```

商品状态参数只允许 ON_SALE，查询 ID 参数的位置精确绑定。购物车商品名称和金额由应用查 products 并计算，不使用隐藏的数据库 JOIN 或 mock 直接返回 HTTP 对象。

- CartService.add(userId, productId, quantity) 使用 Spring 代理调用的 `@Transactional(isolation=Isolation.READ_COMMITTED)`：查商品校验上架/数量 → 查当前用户对应购物车 → 不存在则 INSERT 并用 KeyHolder 取得 ID，存在则 UPDATE → 重新读取 → 返回 created 标记和 DTO。Controller 按 created 返回 201/200。GET `/api/cart` 返回 items 及以分为单位的 totalCents。样例不扣库存，规则来自 QA，不由 mock 猜测。
- TestIdentity 仅在 mock profile 中从 `X-Test-User-Id` 解析测试身份，未提供或非声明用户返回错误；普通业务服务始终从此身份取得 userId。测试身份配置不覆盖生产登录逻辑。页面和 HTTP 测试均用同一身份来源，不把 user_id 固定写在 SQL 结果中。
- application-mock.properties 使用 X_MOCK_MYSQL_URL 和测试凭据；关闭 SQL 初始化、Flyway/Liquibase/ORM migration；固定 Hikari 的 TRANSACTION_READ_COMMITTED；探活时限独立于探索查询。schema.sql 仅由准备插件读取，任何测试都不启动 MySQL、H2 或 SQLite。
