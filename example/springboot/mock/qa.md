# 商品查询与下单 E2E

目标：用户浏览商品并购买2件，订单真实写入、库存真实扣减，其他用户不可查看该订单。

起点与身份：从首页开始。U1=2001、U2=2002使用测试身份请求头；不验证真实登录或支付。初始商品P1=1001，名称“测试键盘”，已上架，单价99元人民币，库存10。所有用户的订单为空，订单自增标识从9001开始。

| 步骤 | 操作 | 固定预期 |
| --- | --- | --- |
| S1 | 打开首页查询商品 | 仅一件测试键盘，单价99元 |
| S2 | 查看商品1001详情 | 名称、价格与列表一致，库存10 |
| S3 | U1购买2件 | 返回201，订单9001，数量2、金额198元，状态CREATED |
| S4 | U1查询订单9001和自己的订单列表 | 返回持久化到mock状态的同一订单，仅一条记录；商品库存8 |
| S5 | U2查询订单9001及订单列表 | 单条查询404，列表为空，不泄露U1订单 |
| S6 | U1购买99件、查询/购买不存在的9999商品，或数量0下单 | 库存不足409，商品不存在404，非法数量400；无新增订单，库存仍为8 |

不带有效测试身份查询/提交订单必须401。浏览器执行S1–S4；真实HTTP测试额外验证S5–S6及401。两种测试各从新环境开始，不共享终态。

业务规则：以商品当前单价计算金额，协议和API中的金额单位均为整数“分”；下单立即扣库存。库存扣减与订单INSERT在同一事务内完成，失败全部回滚。订单记录商品名、单价快照和用户归属。有限示例允许内部订单ID9001–9010、数量1–10、库存0–10，不任意改变上述用例的数量2和终态。没有付款、退款、取消订单或真实登录服务；并发采用等值库存检查和mock事务冲突检测，不声称完整生产数据库语义。

固定初态：products一行，purchase_orders为空。固定终态：products/1001库存8，其余属性不变；U1恰好一张9001订单，数量2、金额19800分、状态CREATED；U2无订单。

Coding Agent读取此QA、应用源码、配置与DDL后，经MCP提交候选。参考商品在场景准备时提供；订单和库存变化必须由应用SQL请求产生，不能预装订单或用HTTP成功响应代替。场景、源码摘要和两端插件版本均固定。每次独立运行重置状态，不安装/启动MySQL或替代数据库，不配置额外模型API。
